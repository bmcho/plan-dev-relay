# plan-dev-relay

Claude Code 세션 두 개를 **기획 세션**과 **개발 세션**으로 짝지어 주는 mod입니다.

사용자는 기획 세션에만 요청합니다. 기획 세션은 일을 정리해서 개발 세션에 지시하고, 개발 세션은 지시를 받는 즉시 작업합니다. 개발 세션의 작업이 끝나면 결과가 기획 세션에 자동으로 보고됩니다. 보고가 오면 기획 세션은 지시의 완료 조건과 계획에 맞게 개발됐는지 바로 **검수**하고 **검수 보고서**를 씁니다. 검수 뒤에 기획 세션이 어디까지 스스로 할지는 `/relay`로 정합니다. 수동은 검수만, 오토는 반려면 다시 지시까지, 풀오토는 계획과 결정, 다음 작업 지시까지 스스로 합니다. 오간 지시와 보고, 검수 보고서, 개발 세션의 작업 내역은 모두 날짜별 로그 파일에 남습니다.

```
            요청                지시 (SendMessage → "dev-session")
  사용자 ─────────▶ 기획 세션 ─────────────────────────────────────▶ 개발 세션
                      ▲                                                 │
                      │    보고 (작업이 끝나면 자동), 기획 세션이 검수    │
                      └─────────────────────────────────────────────────┘

  모든 지시·수신·파일 수정·명령·보고·검수 보고서 ──▶ <logRoot>/<repo 이름>/YYYY-MM-DD.md
```

## 1. 역할별로 하는 일

역할은 두 가지 방식으로 동작합니다.

- **안내문**: `/role`을 입력할 때 모델에게 전달되는 규칙입니다. 모델이 이 규칙을 따라 판단합니다. **강제하지는 않습니다.**
- **mod 동작**: mod 코드가 항상 처리하는 일입니다. 모델의 판단과 관계없이 동작합니다.

### 기획 세션 (`/role plan`)

사용자의 요청을 정리해 구현과 수정을 개발 세션에 맡기고, 돌아온 결과를 검수합니다.

**안내문 (기획 모델이 받는 규칙)**

- 구현과 수정은 직접 하지 않고 개발 세션에 지시한다.
- 서브에이전트에게도 구현이나 수정을 맡기지 않는다. 서브에이전트는 찾기, 조사, 설계 비교, 테스트 실행에만 쓴다. 파일 고치기, 지우기, 커밋, push는 개발 세션에 지시한다.
- 지시는 SendMessage로 보내고, `to`에는 `"dev-session"`을 쓴다.
- 지시의 첫 줄에는 작업 제목을 쓰고, 이어서 목표, 대상 파일, 완료 조건을 적는다. 완료 조건은 검수할 수 있게 항목별로 적는다.
- 개발 세션이 등록되지 않았으면 사용자에게 다른 세션에서 `/role dev`를 입력해 달라고 요청한다.
- 개발 세션의 보고가 오면 검수한다. 검수 때는 파일 읽기, `git diff`, 테스트 실행을 직접 한다.
- 보고를 기다리며 폴링하지 않는다.
- 계획 단계도 TaskCreate·TaskUpdate(없으면 TodoWrite)로 적고 진행에 맞춰 상태를 바꾼다. 이 목록은 개발 세션 화면에도 보인다.

**mod 동작**

- 기획 모델이 `"dev-session"`(또는 개발 세션 id) 앞으로 보낸 메시지를 가로채서, 등록된 개발 세션으로 전달합니다. SendMessage는 세션 id를 주소로 받지 않기 때문에 mod가 대신 보냅니다.
- 기획 모델이 받은 보고의 발신자 이름이나 주소로 답장해도 개발 세션에 보내는 지시로 알아봅니다. mod가 짝 개발 세션의 보고에서 이 값을 배워 둡니다. 그 개발 세션의 보고를 한 번도 받기 전에 이름으로 보낸 지시는 알아보지 못합니다.
- 개발 세션이 등록되어 있지 않으면 전달을 거절하고, 그 이유를 모델에게 돌려줍니다.
- 보낸 지시를 로그에 `[기획→개발] 지시`로 남깁니다.
- 개발 세션의 보고가 오면 "개발 보고 도착 (검수 시작)" 알림을 띄우고, 보고 앞에 검수 요청과 절차를 붙여 기획 모델에 넘깁니다. 모드와 관계없이 기획 세션은 바로 검수를 시작합니다.
- 검수가 끝나면 기획 모델의 마지막 답변(검수 보고서)을 로그에 `[기획] 검수 보고 (통과)` 또는 `(반려)`로 남기고 알림을 띄웁니다. 판정 줄이 없으면 `[기획] 검수 보고 누락`으로 남깁니다.
- 검수 뒤에 기획 세션이 어디까지 스스로 할지는 `/relay`로 정합니다(수동, 오토, 풀오토). 자세한 내용은 [검수와 진행 모드](#검수와-진행-모드-relay)를 보세요.
- 개발 세션이 아닌 다른 수신자에게 보내는 메시지는 표식만 붙여 그대로 보냅니다.
- 기획 세션이 고치는 일을 직접 하지 못하게 막고, 거절할 때 이유를 돌려줍니다.
  - 기획 메인: Bash로 프로젝트 파일을 지우거나 옮기거나 고치는 명령(rm, mv, cp, `sed -i`, 파일을 쓰는 python, 임시 폴더가 아닌 곳으로의 `>`)과 git add·commit·push·checkout 같은 변경을 막습니다. 읽기, 빌드, 테스트와 프로젝트 폴더 밖(임시 폴더, Claude 메모리 등)의 일은 됩니다. 빌드 산출물(`build` 등)은 지울 수 있습니다. Write·Edit는 계획 문서를 써야 해서 막지 않습니다.
  - 서브에이전트: 더 좁게, Bash는 읽기 명령(grep, rg, find, cat, sed -n, git log·diff·show 등), 테스트 실행(gradle test, npm test, pytest, go test 등), 임시 폴더 쓰기만 됩니다. python은 명령 안의 코드(`-c`, 여기 문서)가 파일을 쓰지 않을 때만 됩니다. Edit, Write, NotebookEdit, Monitor도 쓸 수 없습니다.
  - 이 Claude Code에는 Grep·Glob 도구가 없어 찾기도 Bash로 하므로, Bash를 통째로 막지 않고 명령을 읽어서 가립니다. 셸 문법과 python 코드를 흔한 모양으로만 읽으므로 보안 장치는 아닙니다.

> 안내문은 강제가 아닙니다. 기획 세션에 "직접 고쳐"라고 강하게 요청하면 기획 모델이 직접 파일을 고칠 수도 있습니다. 개발 세션에 맡기려면 "개발 세션에 지시해"라고 요청하세요.

### 개발 세션 (`/role dev`)

기획 세션의 지시를 받아 실제로 코드를 고치고 테스트합니다.

**안내문 (개발 모델이 받는 규칙)**

- 다른 세션이 보낸 메시지는 기획 세션의 작업 지시다.
- 작업 결과는 자동으로 보고되므로, SendMessage로 기획 세션에 따로 답하지 않는다.
- 마지막 답변에는 무엇을 바꿨는지, 테스트 결과, 남은 문제를 적는다.
- 단계가 여럿인 지시는 TaskCreate·TaskUpdate(없으면 TodoWrite)로 단계를 적고 진행에 맞춰 상태를 바꾼다. 이 목록은 기획 세션 화면에도 보인다.

**mod 동작**

- 짝인 기획 세션의 지시가 오면 그 지시를 "현재 작업"으로 기록합니다. 세션이 쉬고 있으면 바로 작업이 시작됩니다.
- 작업하는 동안 다음을 모읍니다.
  - 수정한 파일: Edit, Write, NotebookEdit 도구로 바꾼 파일
  - 실행한 명령: Bash 명령과 성공/실패
- 작업(turn)이 끝나면 기획 세션에 보고를 보냅니다. 개발 모델이 띄운 서브에이전트가 아직 일하면 보고를 미룹니다. 서브에이전트가 끝나면 개발 모델이 결과를 받아 마무리하고, 그 turn이 끝날 때 보고합니다. 서브에이전트가 고친 파일과 실행한 명령도 보고에 들어갑니다.
- 보고 형식:

  ```
  [개발 보고] <지시의 첫 줄>

  <개발 모델의 마지막 답변>

  추가로 받은 지시:          ← 작업 중에 지시가 더 왔을 때만
  - <추가 지시의 첫 줄>

  검수 기준 (원래 지시):     ← 기획 세션이 검수할 때 맞춰 볼 기준
  <기획 세션이 보낸 지시 원문>

  수정 파일 (Edit·Write 도구):
  - src/main/java/.../FooService.java

  명령:
  - 성공: ./gradlew test
  ```

- 마지막 답변이나 원래 지시가 8,000자를 넘으면 보고에서는 자르고 `전체 내용: <로그 파일 경로>`를 붙입니다. 로그에는 전체가 남습니다.
- 작업이 중단되거나 오류·거절로 끝나면 답변 앞에 `(중단됨)`, `(오류로 종료)`, `(거절로 종료)`를 붙입니다.
- 작업 중에 지시가 또 오면 첫 지시를 유지하고, 새 지시는 보고의 `추가로 받은 지시`에 적습니다.
- 사람이 개발 세션에 직접 입력한 작업은 로그에만 남기고 기획 세션에는 보고하지 않습니다. 직접 입력한 작업을 하는 도중에 지시가 오면 그 지시 작업으로 바뀌고, 그때까지의 기록은 유지됩니다.

### 두 역할 공통

- **상태 줄 캐릭터**: 프롬프트 위에 역할별 Claude 캐릭터를 보여 줍니다. 작업 중에는 움직이고, 쉬는 중에는 흐린 색으로 멈춥니다. 모델의 turn이 끝났어도 모델이 띄운 서브에이전트가 일하는 동안은 작업 중으로 봅니다. 작업 중이면 이름표 옆에 지시 제목이 나옵니다. 캐릭터 발 밑에는 메인 모델과 effort가 흐린 글자로 작게 나옵니다(예: `opus-5-5 · max`). 메인이 마지막으로 보낸 모델 요청의 값이어서, 모델이나 effort를 바꾸면 메인의 다음 요청부터 바뀝니다. 첫 요청 전에는 세션 모델만 나오고, effort를 받지 않는 모델은 effort가 나오지 않습니다. 서브에이전트의 모델은 나오지 않습니다. band가 캐릭터 높이(5줄)만큼만 쓸 수 있으면 이 줄은 나오지 않습니다. 데스크톱 앱에서는 캐릭터를 고정폭 글꼴로, 모델 줄을 작은 글자로 그립니다.

  ```
  기획 (파란 이름표)                         개발 (초록 이름표)
              .oO( ? )                        ▄███▄
   ▐▛███▜▌   ┌────────┐                      ▐▛███▜▌   ┌────────┐
  ▝▜█████▛▘──│ ☐ 요구 │   기획 중           ▝▜█████▛▘  │ >_ ▌   │   개발 중
    ▘▘ ▝▝    │ ☐ 설계 │                       ▘▘ ▝▝    └──┬──┬──┘
             └────────┘                                    ═╧══╧═
  opus-5-5 · max                            opus-5-5 · max
  ```

- **To-Do 목록**: 캐릭터 옆 이름표 아래에 두 세션이 같은 To-Do 목록을 보여 줍니다.

  ```
  기획 To-Do  완료 1/3
   ☑ 요구 정리
   ▶ 구현 계획 작성 후 개발 세션에 지시
  릴레이 To-Do  완료 1/3
   ▶ 회원가입 API 오류 처리  개발 중
      ☑ 예외 클래스 추가
      ▶ 단위 테스트 작성
      ☐ README 갱신
  ```

  - `기획 To-Do`는 기획 에이전트가 적은 단계입니다. 릴레이 행 아래의 단계는 개발 에이전트가 그 지시를 하며 적은 단계입니다. 두 에이전트가 TaskCreate·TaskUpdate(또는 TodoWrite)로 적은 단계를 mod가 모읍니다. 서브에이전트의 단계와, 개발 세션에 사람이 직접 입력한 작업의 단계는 넣지 않습니다.
  - `릴레이 To-Do`는 가장 최근 지시와 그 상태입니다: ▶ 개발 중, ◇ 검수 중, ☑ 통과, ✗ 반려. 반려된 행은 다음 지시가 올 때까지 남습니다. 개발 중에 보낸 추가 지시는 아래에 이어 붙습니다.
  - 기획 단계가 모두 완료되고 릴레이 행이 모두 통과하면, 그 turn이 끝날 때 목록을 비웁니다. 개발 세션 화면에서도 2초쯤 뒤에 사라집니다.
  - 그 전까지 완료한 단계는 지우지 않고 ☑로 남깁니다. 목록은 band가 쓸 수 있는 줄을 모두 쓰고, 긴 항목은 자르지 않고 다음 줄로 접습니다. 그래도 줄이 모자라면 진행 중인 단계 주변만 보이고, 전체 진행은 제목 줄의 `완료 n/m`로 봅니다.
  - 에이전트가 TaskList로 작업 목록을 보면 mod도 그 결과로 목록을 맞춥니다. Claude Code가 이미 치운 단계는 빠집니다. `/role`을 다시 입력하면 목록을 새로 시작합니다.
  - 두 세션은 2초마다 공유 파일(`todo-plan.json`, `todo-dev.json`)로 목록을 주고받습니다. 상대 화면에는 최대 약 4초 늦게 보입니다.
  - 단계 기록은 안내문이라 강제되지 않습니다. 에이전트가 단계를 적지 않으면 릴레이 행만 보입니다.
- **발신 표식**: 두 세션이 주고받는 메시지 첫 줄에 `[plan-dev-relay role=<역할> session=<세션 id>]` 표식을 붙입니다. 받는 쪽은 이 표식으로 짝의 메시지인지 확인하고, 표식은 지운 뒤 모델에 넘깁니다. 표식이 없거나 짝이 아닌 세션의 메시지는 mod가 건드리지 않습니다. 표식은 구별용이며 보안 장치가 아닙니다.
- **짝 맺기**: repo마다 기획 하나, 개발 하나가 짝이 됩니다. 짝 정보는 `roles.json`에 저장되고, 같은 역할을 다른 세션이 등록하면 그 세션으로 바뀝니다.
- **서브에이전트**: 모델이 Agent 도구로 띄우는 서브에이전트를 다룹니다.
  - 안내문 (두 역할 공통): 찾기·위치 파악은 Explore로 띄운다. 서브에이전트의 model은 사용자가 모델을 지정했을 때만 적고, 그 밖에는 비워 둔다. 강제되지 않습니다.
  - 모델 기본값: 호출에 model이 없으면 종류별 기본 모델로 띄웁니다. Explore, claude-code-guide, statusline-setup은 `haiku`, 기획 세션의 general-purpose는 `sonnet`입니다. 개발 세션의 general-purpose와 Plan 같은 나머지는 세션 모델을 씁니다. 플러그인·커스텀 에이전트는 자기 정의를 따르고, 호출이 적은 model은 그대로 둡니다. 별칭은 Claude Code가 그 버전이 아는 최신 모델로 바꿉니다. Claude Code를 업데이트하면 새로 띄운 세션부터 새 모델이 쓰입니다.
  - 동시 상한: 메인 모델이 띄운 서브에이전트 중 일하는 것이 `maxAgents`개(기본 3개)면 새 에이전트를 띄우지 않고, 그 이유를 모델에게 돌려줍니다. 한 메시지로 여러 개를 띄워도 상한을 넘지 않습니다. 상한은 `/subagents N`으로 바꿉니다.
  - effort: 서브에이전트가 모델에 요청할 때마다 모델에 맞는 effort를 줍니다. 기본값은 haiku `low`, sonnet `high`, opus `high`입니다. 설정에 적지 않은 모델(fable 등)과 메인 모델은 세션 설정을 따릅니다. 모델별 레벨은 `/agentEffort 모델 레벨`로 바꿉니다.
  - 팀원, 워크플로 에이전트, 이어 하는 에이전트에는 모델 기본값과 상한을 적용하지 않습니다.

## 3. 설치

### 방법 A. 마켓플레이스로 설치 (추천)

이 저장소는 플러그인이면서 마켓플레이스입니다. Claude Code 안에서 두 줄이면 설치됩니다.

```
/plugin marketplace add bmcho/plan-dev-relay
/plugin install plan-dev-relay@plan-dev-relay
```

- `bmcho/plan-dev-relay`는 GitHub 저장소 https://github.com/bmcho/plan-dev-relay 를 줄여 쓴 주소입니다.
- 터미널에서 설치할 수도 있습니다.

  ```
  claude plugin marketplace add bmcho/plan-dev-relay
  claude plugin install plan-dev-relay@plan-dev-relay
  ```

- 설치한 뒤 **새로 띄운 세션부터** 적용됩니다.
- 설치 확인: 새 세션에서 `/role`을 입력했을 때 `역할 없음. 사용법: /role plan | dev | off`가 나오면 설치된 것입니다.
- 데스크톱 앱도 같은 사용자 설정 폴더(`~/.claude`, Windows는 `%USERPROFILE%\.claude`)의 플러그인을 씁니다. 터미널에서 설치하면 데스크톱 앱에서 새로 연 Code 세션에도 적용됩니다.

### 방법 B. 프로젝트에 등록해서 팀원에게 안내하기

팀이 함께 쓰는 프로젝트의 `.claude/settings.json`에 아래 내용을 넣으면, 팀원이 그 프로젝트를 열 때 설치 안내가 나옵니다.

```json
{
  "extraKnownMarketplaces": {
    "plan-dev-relay": {
      "source": { "source": "github", "repo": "bmcho/plan-dev-relay" }
    }
  },
  "enabledPlugins": { "plan-dev-relay@plan-dev-relay": true }
}
```

직접 고치는 대신 `claude plugin marketplace add <주소> --scope project`를 실행해도 마켓플레이스 등록이 들어갑니다.

### 방법 C. 폴더로 직접 불러오기 (mod를 고치면서 쓸 때)

```
git clone https://github.com/bmcho/plan-dev-relay.git
```

`~/.claude/settings.json`(Windows는 `%USERPROFILE%\.claude\settings.json`)에 clone한 폴더 경로를 넣습니다.

```json
{
  "env": { "CLAUDE_CODE_PLUGIN_DIRS": "/절대/경로/plan-dev-relay" }
}
```

- 한 번만 써 보려면 `claude --plugin-dir /절대/경로/plan-dev-relay`로 실행합니다.
- 실행 중인 세션은 이 폴더를 감시하므로, 파일을 고쳐 저장하면 mod가 다시 불러와집니다.
- **방법 A와 함께 쓰지 마세요.** 같은 mod가 두 번 불려 hook이 두 번 실행됩니다(로그와 보고가 두 번씩 남음).

### 업데이트

```
claude plugin marketplace update plan-dev-relay
claude plugin update plan-dev-relay@plan-dev-relay
```

업데이트는 세션을 다시 시작해야 적용됩니다. 방법 C는 `git pull`만 하면 됩니다.

### 제거

```
claude plugin uninstall plan-dev-relay@plan-dev-relay
claude plugin marketplace remove plan-dev-relay
```

로그 폴더는 지워지지 않습니다. 필요하면 직접 지우세요.

## 4. 설정

| 설정 | 기본값 | 설명 |
| --- | --- | --- |
| `logRoot` (로그 폴더) | `~/Documents/claude/plan-dev-log` | 로그와 `roles.json`을 둘 폴더입니다. repo마다 하위 폴더가 생깁니다. `~`는 홈 폴더(Windows는 `USERPROFILE`)로 바뀝니다. |
| `maxAgents` (서브에이전트 상한) | `3` | 기획·개발 세션에서 동시에 일하는 서브에이전트 수의 상한입니다. `0`이면 제한하지 않습니다. |
| `subagentEffort` (서브에이전트 effort) | `haiku=low sonnet=high opus=high` | 서브에이전트가 모델별로 쓸 effort입니다. `모델=레벨` 쌍을 공백이나 쉼표로 나눠 한 줄에 적습니다. 모델은 haiku, sonnet, opus, fable, 레벨은 low, medium, high, xhigh, max입니다. 적지 않은 모델은 세션 설정을 따르고, 비워 두면 effort를 바꾸지 않습니다. |

바꾸는 방법은 넷 중 하나입니다. 바꾼 값은 mod를 다시 불러오면서 바로 적용됩니다.

- `maxAgents`와 `subagentEffort`는 세션 안에서 `/subagents`, `/agentEffort` 명령으로 바꿉니다([명령](#명령) 참고).
- Claude Code의 `/config`나 `/plugin` 메뉴에서 plan-dev-relay의 항목을 바꿉니다.
- 설치할 때 지정합니다.

  ```
  claude plugin install plan-dev-relay@plan-dev-relay --config logRoot=/원하는/경로
  ```

- 설치 뒤 터미널에서 바꿉니다.

  ```
  echo '{"logRoot":"/원하는/경로"}' | claude plugin configure plan-dev-relay@plan-dev-relay --values-stdin
  echo '{"maxAgents":2,"subagentEffort":"haiku=low sonnet=medium opus=max"}' | claude plugin configure plan-dev-relay@plan-dev-relay --values-stdin
  ```

`claude plugin configure plan-dev-relay@plan-dev-relay`를 옵션 없이 실행하면 현재 설정을 볼 수 있습니다.

## 5. 사용법

### 시작하기

1. 터미널 A에서 repo 폴더로 이동해 `claude`를 실행하고 `/role plan`을 입력합니다.
2. 터미널 B에서 **같은 repo 폴더**로 이동해 `claude`를 실행하고 `/role dev`를 입력합니다.
3. 두 세션의 **권한 모드를 같게** 맞춥니다(예: 둘 다 auto). 다르면 메시지가 승인 대기에 걸릴 수 있습니다([문제 해결](#7-문제-해결) 참고).

데스크톱 앱에서는 터미널 대신 같은 repo 폴더로 Code 세션을 두 개 열고, 한쪽에 `/role plan`, 다른 쪽에 `/role dev`를 입력합니다.

### 일 맡기기

1. 기획 세션(A)에 평소처럼 요청합니다.
   - 예: `로그인 API에 입력값 검증을 추가하도록 개발 세션에 지시해`
2. 기획 모델이 지시를 정리해서 개발 세션에 보냅니다.
3. 개발 세션(B)이 지시를 받아 바로 작업합니다. 상태 줄의 개발 캐릭터가 움직입니다.
4. 작업이 끝나면 기획 세션에 "개발 보고 도착 (검수 시작)" 알림이 뜨고, 기획 세션이 바로 검수합니다.
5. 기획 세션이 검수 보고서를 씁니다. 통과면 끝입니다. 반려면 수동 모드에서는 사용자가 다시 지시할지 정합니다.
   - 예: `반려된 부분 다시 지시해`

### 검수와 진행 모드 (`/relay`)

개발 보고가 오면 기획 세션은 **모드와 관계없이 바로 검수**합니다. mod가 보고 앞에 검수 요청을 붙여 기획 모델에 넘기고, 기획 모델은 아래 절차를 따릅니다.

1. 보고의 `검수 기준 (원래 지시)`에 적힌 완료 조건과 기획 세션의 계획(계획 문서가 있으면 그 문서)에 맞는지 항목마다 확인합니다.
2. 보고만 믿지 않고 `git diff`, 바뀐 파일 읽기, 테스트 실행으로 직접 확인합니다. 코드는 고치지 않습니다.
3. 그 turn의 마지막 답변으로 검수 보고서를 씁니다.

검수 보고서 형식:

```
[검수 보고] <작업 제목>
검수 결과: 통과 | 반려
완료 조건 확인:
- <조건>: 충족 | 미충족 — <근거>
확인 방법:
- <실행한 명령이나 읽은 파일>: <결과>
문제와 고칠 점: <반려일 때 고칠 점, 통과면 없음>
결정: <스스로 정한 것과 근거>            ← 풀오토만
다음 지시: <보낸 지시의 제목>             ← 풀오토만
사용자 확인 필요: <멈춘 이유, 없으면 없음> ← 풀오토만
```

검수 turn이 끝나면 mod가 검수 보고서 전체를 로그에 `[기획] 검수 보고 (통과)` 또는 `[기획] 검수 보고 (반려)`로 남기고 알림을 띄웁니다. 마지막 답변에 `검수 결과:` 줄이 없으면 `[기획] 검수 보고 누락`으로 남기고 경고 알림을 띄웁니다. 사용자가 직접 "다시 검수해 줘"라고 시킨 검수도, 답변에 `검수 결과:` 줄이 있으면 같은 방식으로 남습니다. 기획 모델이 검수를 서브에이전트에 맡기고 판정 줄 없이 turn을 끝내면, 서브에이전트가 끝난 뒤 이어지는 turn까지 기다렸다가 남깁니다.

`/relay`는 **검수 뒤에 기획 세션이 어디까지 스스로 할지**를 정합니다. 기획 세션에서 입력합니다.

| 모드 | 통과면 | 반려면 | 최대 횟수 |
| --- | --- | --- | --- |
| 수동 (기본값, `/relay manual`) | 멈춤 | 멈춤. 다시 지시할지는 사용자가 정함 | 없음 |
| 오토 (`/relay auto [N]`) | 멈춤 | 이번 검수에서 나온 고칠 점만 다시 지시. 새 작업이나 다음 단계는 지시하지 않음 | 기본 3회 (1~10) |
| 풀오토 (`/relay full [N]`) | 계획의 다음 작업을 정해 지시 | 고칠 점을 다시 지시 | 기본 20회 (1~50) |

오토의 흐름:

```
개발 보고 → 검수 (오토 1/3) → 반려 → 다시 지시 → 개발 작업 → 보고
          → 검수 (오토 2/3) → 통과 → 검수 보고서 (멈춤)
```

#### 풀오토

기획, 계획, 결정, 검수, 다시 지시, 다음 작업 지시를 기획 세션이 사용자에게 묻지 않고 스스로 합니다.

1. 기획 세션에서 `/relay full`을 입력합니다.
2. 기획 세션에 목표를 줍니다. 예: `TMS 경로 API를 설계부터 구현까지 끝내 줘`
3. 기획 세션이 계획을 세워 계획 문서에 적고, 승인 없이 첫 작업을 지시합니다. 설계나 계획 승인, 선택지 결정도 스스로 합니다.
4. 보고가 올 때마다 검수합니다. 반려면 고칠 점을 다시 지시하고, 통과면 계획 문서에서 다음 작업을 정해 지시합니다.
5. 계획이 모두 끝나면 마지막 검수 보고서를 쓰고 멈춥니다.

```
목표 → 계획 문서 → 지시 → 개발 → 보고 → 검수 (풀오토 1/20) → 통과 → 다음 작업 지시 → …
                                                         → 반려 → 고칠 점 다시 지시 → …
```

- **결정 기록**: 스스로 내린 결정은 근거와 함께 지시문과 검수 보고서의 `결정:` 항목에 적습니다. 둘 다 로그에 전문이 남으므로, 로그에서 `결정:`을 찾아 확인할 수 있습니다.
- **멈추는 경우**:
  - 계획이 모두 끝났을 때
  - 되돌리기 어렵거나 바깥으로 나가는 작업(git push, 배포, 운영 데이터 삭제, 외부 전송)이 필요할 때: 그 작업은 지시하지 않고, 검수 보고서의 `사용자 확인 필요`에 이유를 적고 멈춥니다. `[기획] 사용자 확인 필요` 로그와 알림이 따로 남습니다. 사용자가 기획 세션에 답하면 이어서 진행합니다.
  - 최대 횟수(기본 20회)에 닿았을 때: 그다음 보고는 검수만 하고 멈추며 "풀오토 한도 N회 도달" 알림을 띄웁니다. 기획 세션에 `계속해`처럼 입력하면 횟수가 0으로 돌아가 다시 이어 갑니다.
- **멈추게 하려면** 기획 세션에서 `/relay manual`을 입력하세요. Esc는 지금 turn만 멈춥니다. 이미 보낸 지시나 보고가 있으면 그 뒤로 다시 이어질 수 있습니다.
- 두 세션 모두 권한 확인 창이 뜨지 않는 권한 모드여야 사람 없이 이어집니다. 확인 창이 뜨면 그 자리에서 기다립니다.
- 되돌리기 어려운 작업 앞에서 멈추는 규칙은 안내문입니다. 마지막 방어선은 각 세션의 Claude Code 권한 모드입니다.

알아 둘 점:

- 사용자가 기획 세션에 직접 프롬프트를 입력하면 오토와 풀오토의 진행 횟수가 0으로 돌아갑니다.
- 모드는 세션마다 정해집니다. 세션을 새로 띄우면 수동 모드로 시작합니다.
- 검수 때마다 기획 세션이 확인 명령과 테스트를 실행하므로 시간과 토큰이 더 듭니다. 오토와 풀오토는 사람 없이 두 세션이 주고받으므로 더 많이 쓰고, 풀오토가 가장 많이 씁니다.
- 검수 절차는 안내문이라 강제되지 않습니다. 판정 줄이 빠진 검수는 로그의 `검수 보고 누락`으로 확인하세요.

| 명령 | 하는 일 |
| --- | --- |
| `/role plan` | 이 세션을 기획 세션으로 등록하고, 기획 안내문을 모델에 전달합니다. |
| `/role dev` | 이 세션을 개발 세션으로 등록하고, 개발 안내문을 모델에 전달합니다. |
| `/role` | 현재 역할과 상대 세션 id를 보여 줍니다. |
| `/role off` | 역할을 지우고 `roles.json`에서 이 세션 항목을 지웁니다. 다른 세션이 같은 역할로 다시 등록했으면 그 항목은 남깁니다. |
| `/relay` | 현재 모드(수동/오토/풀오토)와 사람 없이 이어 간 횟수를 보여 줍니다. |
| `/relay manual` | 수동 모드로 바꿉니다(기본값). 검수만 합니다. 오토나 풀오토를 멈출 때도 씁니다. |
| `/relay auto [N]` | 오토 모드로 바꿉니다. N은 다시 지시하는 최대 횟수(1~10, 기본 3)입니다. |
| `/relay full [N]` | 풀오토 모드로 바꿉니다. N은 사람 없이 이어 가는 최대 검수 횟수(1~50, 기본 20)입니다. |
| `/subagents` | 동시에 일하는 서브에이전트 상한(`maxAgents`)을 보여 줍니다. |
| `/subagents N` | 상한을 N개로 바꿉니다. `0`이면 제한하지 않습니다. |
| `/agentEffort` | 서브에이전트의 모델별 effort(`subagentEffort`)를 보여 줍니다. |
| `/agentEffort 모델 레벨` | 한 모델의 effort를 바꾸고 다른 모델은 그대로 둡니다. 예: `/agentEffort sonnet m`. 모델은 haiku, sonnet, opus, fable입니다. 레벨은 `l`(low), `m`(medium), `h`(high), `xh`(xhigh), `max`로 줄여 쓰거나 전체 이름으로 씁니다. |

`/subagents`와 `/agentEffort`로 바꾼 값은 `/config`에서 바꾼 것과 같은 플러그인 설정에 저장됩니다. 역할이 없는 세션에서도 쓸 수 있습니다.

### 알아 두면 좋은 점

- 역할은 **세션마다** 정합니다. 세션을 새로 띄우면 `/role`을 다시 입력합니다.
- 개발 세션을 바꾸고 싶으면 새 세션에서 `/role dev`를 입력하면 됩니다. 이전 개발 세션은 짝에서 빠집니다.
- 개발 세션에서도 사람이 직접 작업을 시킬 수 있습니다. 이 작업은 로그에만 남고 기획 세션에는 보고되지 않습니다.

## 6. 로그

| 파일 | 경로 |
| --- | --- |
| 날짜별 로그 | `<logRoot>/<repo 이름>/YYYY-MM-DD.md` |
| 짝 정보 | `<logRoot>/<repo 이름>/roles.json` |
| To-Do 공유 (기획) | `<logRoot>/<repo 이름>/todo-plan.json` |
| To-Do 공유 (개발) | `<logRoot>/<repo 이름>/todo-dev.json` |

To-Do 공유 파일은 각 세션이 자기 몫만 2초마다 덮어씁니다. To-Do 단계는 날짜별 로그에 남기지 않습니다.

두 세션이 같은 로그 파일에 시간순으로 기록합니다. 기록 예:

```markdown
# control-center plan-dev log 2026-10-14

## 13:49:24 [기획→개발] 지시 (<기획 세션 id> → <개발 세션 id>)
빈 텍스트 파일 생성
목표: 저장소 루트에 빈 텍스트 파일 하나를 만든다.
...

## 13:49:24 [개발] 수신 (<기획 세션 id> → <개발 세션 id>)
...

## 13:50:26 [개발] 명령 성공
`touch empty.txt`

## 13:50:43 [개발→기획] 보고 (<개발 세션 id> → <기획 세션 id>)
[개발 보고] 빈 텍스트 파일 생성
...

## 13:50:43 [기획] 보고 수신 (<개발 세션 id> → <기획 세션 id>)
...

## 13:50:43 [기획] 검수 요청 (수동)
[개발 보고] 빈 텍스트 파일 생성

## 13:51:20 [기획] 검수 보고 (통과)
[검수 보고] 빈 텍스트 파일 생성
검수 결과: 통과
...
```

| 항목 | 남기는 쪽 | 내용 |
| --- | --- | --- |
| `역할 등록` | 양쪽 | `/role plan`, `/role dev`를 입력한 세션 id |
| `[기획→개발] 지시` | 기획 | 보낸 지시 원문 |
| `[개발] 수신` | 개발 | 받은 지시 원문 |
| `[개발] 파일 수정` | 개발 | Edit·Write 도구로 바꾼 파일 |
| `[개발] 명령 성공/실패` | 개발 | 실행한 Bash 명령 |
| `[개발→기획] 보고` | 개발 | 보낸 보고 (답변 전체) |
| `[기획] 보고 수신` | 기획 | 받은 보고 |
| `[개발] 직접 입력`, `직접 작업 완료` | 개발 | 사람이 직접 입력한 작업과 그 결과 |
| `전달 실패` | 양쪽 | 지시나 보고를 보내지 못한 이유 |
| `[기획] 릴레이 모드 변경` | 기획 | `/relay`로 바꾼 모드 |
| `[기획] 검수 요청 (…)` | 기획 | 검수를 요청한 보고. 괄호 안은 `수동`, `오토 n/N`, `풀오토 n/N`, `오토 한도 N회 도달`, `풀오토 한도 N회 도달` 중 하나 |
| `[기획] 검수 보고 (통과/반려)` | 기획 | 기획 모델이 쓴 검수 보고서 전체 |
| `[기획] 검수 보고 누락` | 기획 | 검수 turn의 마지막 답변에 `검수 결과:` 줄이 없을 때 그 답변 |
| `[기획] 사용자 확인 필요` | 기획 | 풀오토가 되돌리기 어려운 작업 앞에서 멈춘 이유 |

## 7. 문제 해결

| 증상 | 원인과 해결 |
| --- | --- |
| 개발 세션이 지시를 받고도 작업을 시작하지 않는다 | 두 세션의 권한 모드 종류가 다르면 Claude Code가 다른 세션의 메시지를 **승인 대기**로 붙잡아 둡니다. 두 세션의 권한 모드를 맞추세요. 항상 받으려면 `~/.claude/settings.json`에 `"crossSessionInbound": "accept"`를 넣을 수 있지만, 내 모든 세션이 서로 작업을 시킬 수 있게 되므로 신중히 쓰세요. |
| 기획 세션에 "개발 세션 전달 실패" 알림이 뜬다 | 개발 세션이 등록되지 않았거나 이미 꺼졌습니다. 개발 세션에서 `/role dev`를 다시 입력하세요. |
| 개발 세션에 "기획 세션 전달 실패" 알림이 뜬다 | 기획 세션이 등록되지 않았거나 꺼졌습니다. 보고 내용은 로그에 남아 있습니다. |
| 기획 모델이 직접 코드를 고친다 | 역할 규칙은 안내문이라 강제되지 않습니다. 요청에 "개발 세션에 지시해"라고 명시하세요. 세션을 새로 띄웠다면 `/role plan`을 다시 입력해 안내문을 전달하세요. |
| 기획 모델이 `dev-session`을 모른다 | 안내문은 `/role`을 입력할 때 전달됩니다. `/role plan`을 다시 입력하세요. |
| 반려와 다시 지시가 계속 반복된다 | 기획 모델이 계속 반려하는 경우입니다. 오토와 풀오토는 최대 횟수에서 멈추며, `/relay manual`을 입력하면 바로 멈춥니다. 횟수를 줄이려면 `/relay auto 1`, `/relay full 5`처럼 지정하세요. |
| 풀오토가 멈췄다 | 로그에서 `사용자 확인 필요`나 "풀오토 한도 N회 도달" 알림을 확인하세요. 기획 세션에 답하거나 `계속해`라고 입력하면 이어서 진행합니다. |
| 풀오토가 멈추지 않는다 | 기획 세션에서 `/relay manual`을 입력하세요. Esc는 지금 turn만 멈춥니다. |
| 개발 세션의 turn이 끝났는데 보고가 오지 않는다 | 개발 모델이 띄운 서브에이전트가 아직 일하면 보고를 미룹니다. 이름표가 `개발 중`이면 아직 일하는 중입니다. 서브에이전트가 끝나면 개발 모델이 마무리하고, 그 turn이 끝날 때 보고합니다. |
| 보고가 와도 검수를 시작하지 않는다 | 두 세션의 권한 모드가 다르면 보고가 승인 대기에 걸릴 수 있습니다. 두 세션의 권한 모드를 맞추세요. |
| 로그에 `검수 보고 누락`이 남는다 | 기획 모델이 검수 보고서 형식을 따르지 않았거나 검수가 중단됐습니다. 기획 세션에 "검수 보고서 형식으로 다시 검수해 줘"라고 요청하면, 그 답변이 검수 보고로 남습니다. |
| 로그와 보고가 두 번씩 남는다 | 마켓플레이스 설치(방법 A)와 폴더 불러오기(방법 C)를 함께 쓰고 있습니다. 하나만 쓰세요. |
| 로그 파일이 생기지 않는다 | `logRoot` 경로에 쓰기 권한이 있는지 확인하세요. |
| "roles.json이 깨져서…" 메시지가 보인다 | 짝 정보 파일이 손상되었습니다. 빈 짝 정보로 계속 동작하며, 양쪽에서 `/role`을 다시 입력하면 새로 써집니다. |
| To-Do 목록이 보이지 않는다 | 에이전트가 TaskCreate·TaskUpdate(또는 TodoWrite)로 단계를 적지 않았습니다. 안내문은 강제가 아니므로 "단계를 TaskCreate로 적어 줘"라고 요청하세요. 릴레이 행은 지시를 보내면 나타납니다. |
| 상대 세션의 목록이 보이지 않거나 늦게 바뀐다 | 목록은 2초마다 공유 파일로 주고받아 최대 약 4초 늦습니다. 두 세션이 같은 repo에서 `/role`을 입력했는지, `logRoot`에 쓰기 권한이 있는지 확인하세요. |
| 서브에이전트가 "상한 N개에 닿았습니다" 오류로 뜨지 않는다 | 메인 모델이 띄운 서브에이전트 중 일하는 것이 `maxAgents`개입니다. 하나가 끝나면 다시 띄울 수 있습니다. 더 띄우려면 `/subagents N`으로 상한을 늘리거나 `/subagents 0`으로 상한을 없애세요. |
| "서브에이전트 effort 설정에서 무시한 값" 알림이 뜬다 | `subagentEffort`에 알아보지 못한 쌍이 있습니다. 알아본 쌍은 그대로 적용됩니다. 형식은 `haiku=low sonnet=high opus=high`이고, 레벨은 low, medium, high, xhigh, max입니다. |
| 캐릭터 발 밑에 effort가 나오지 않는다 | 메인이 아직 모델 요청을 보내지 않았거나, 그 모델이 effort를 받지 않습니다. 첫 요청을 보내면 나옵니다. |
| `/role`이 `역할 명령 실패 (…)`를 보인다. 예전 버전에서는 `plan-dev-relay registered /role but no command.run hook answered it`가 나온다 | `/role`이 실패했습니다. 괄호 안이 이유입니다. 흔한 이유는 로그 폴더(`logRoot`)에 `roles.json`을 쓰지 못한 경우입니다. macOS 데스크톱 앱은 터미널과 따로 문서 폴더 접근을 허용해야 할 수 있습니다(시스템 설정 > 개인정보 보호 및 보안 > 파일 및 폴더). Windows는 Windows 보안의 '제어된 폴더 액세스'가 문서 폴더 쓰기를 막을 수 있습니다. 아니면 `logRoot`를 쓸 수 있는 폴더로 바꾸세요. |
| `cc-plugin-sec-default runs first and sent the event on past it` 알림이 뜬다 | Team·Enterprise 조직이나 관리 설정이 있는 컴퓨터에서는 Claude Code에 들어 있는 보안 기본 플러그인이 mod의 시스템 프롬프트 추가(`prompt.compose`)를 건너뜁니다. 역할 안내문은 `/role` 결과로, 검수 절차는 보고 앞 머리말로 전달되므로 릴레이는 동작합니다. `/role` 오류와는 관계없습니다. |
| 기획 세션에서 `파일을 고칠 수 없습니다`나 `Bash로 파일을 고치거나…`로 막힌다 | 의도된 동작입니다. 고치기, 지우기, 커밋, push는 개발 세션에 지시하세요. 읽기나 테스트인데 막혔다면 목록에 없는 명령, 임시 폴더가 아닌 곳으로의 `>`, 파일을 쓰는 python 코드가 있는지 확인하세요. |
| 개발 단계가 기획 화면의 릴레이 행 아래에 나오지 않는다 | 기획 세션이 그 지시를 알아보지 못했습니다. 기획 세션을 새로 띄운 뒤 아직 지시를 보내지 않았거나, 개발 세션의 보고를 한 번도 받기 전에 개발 세션 이름으로 지시를 보낸 경우입니다. 다음 지시부터 나옵니다. |

## 8. 주의 사항

- **신뢰하는 환경에서만 쓰세요.** 이 mod는 셸 명령(로그 쓰기)을 실행하고, 세션 간 메시지로 다른 세션이 작업을 시작하게 합니다.
- **보고의 "수정 파일"은 Edit·Write·NotebookEdit 도구로 바꾼 파일만 담습니다.** 셸 명령으로 바꾼 파일은 "명령" 목록에서 확인하세요.
- 로그에는 지시와 답변 원문이 그대로 남습니다. 민감한 내용을 다룬다면 로그 폴더 위치와 공유 범위에 주의하세요.
- 검수 때 기획 세션도 같은 폴더에서 테스트를 실행합니다. 그동안 개발 세션에 직접 다른 작업을 시키면 결과가 섞일 수 있습니다.
- **풀오토는 사람 확인 없이 계획과 결정을 진행합니다.** 로그의 `결정:` 항목과 검수 보고서를 자주 확인하고, 중요한 작업에는 오토나 수동을 쓰세요.

## 9. 개발

### 파일 구조

```
plan-dev-relay/
├── .claude-plugin/
│   ├── plugin.json        # 플러그인 정보, userConfig(logRoot, maxAgents, subagentEffort)
│   └── marketplace.json   # 이 저장소를 마켓플레이스로 쓰기 위한 목록 ("./")
├── hooks/
│   ├── hooks.json         # hook 모듈 지정 (register.tsx)
│   ├── register.tsx       # 모든 hook과 $를 쓰는 입출력 함수
│   ├── core.ts            # 순수 함수: 경로, 시각, 표식, 보고, 안내문, 서브에이전트 설정
│   ├── todo.ts            # 순수 함수: To-Do 반영, 릴레이 행, 공유 파일, 목록 줄
│   ├── art.ts             # 순수 함수: 캐릭터 프레임과 이름표 색
│   ├── core.test.ts       # core.ts, art.ts 테스트
│   ├── todo.test.ts       # todo.ts 테스트
│   └── relay.test.ts      # 엔진 수준 시나리오 테스트
└── types/index.d.ts       # $.state 값의 타입 계약
```

### 검증

```
claude plugin test .
claude plugin validate --strict .
claude plugin validate --strict .claude-plugin/plugin.json
```

### 엔진 규칙 (고칠 때 주의)

엔진은 hook 모듈을 불러오기 전에 소스를 검사합니다. 아래 규칙을 어기면 mod가 불려지지 않습니다.

- `$`를 받는 함수는 `register.tsx` 안에 선언해야 합니다. 다른 파일에서 가져온 함수에 `$`를 넘길 수 없습니다.
- `atom({ plugin, key })`의 `plugin`과 `key`는 문자열 리터럴이어야 합니다.
- `$.env.get`의 변수 이름은 문자열 리터럴이어야 합니다.
- 테스트에서 `$` 호출(`session.id`, `fs.*`, `process.run` 등)에 답하는 stub은 `{ value }`로 감싸서 돌려줘야 합니다.

### 새 버전 배포

1. 바뀐 점을 [변경 내역](#10-변경-내역)에 적습니다. 버그 수정은 patch(0.4.1 → 0.4.2), 새 기능·새 명령·눈에 띄는 동작 변경은 minor(0.4.x → 0.5.0)를 올립니다. 문서만 바뀌면 버전을 올리지 않습니다.
2. `.claude-plugin/plugin.json`과 `.claude-plugin/marketplace.json`의 `version`을 함께 올립니다. 마켓플레이스로 설치한 곳은 version이 바뀌어야 업데이트를 받습니다.
3. 테스트와 검증을 통과시킨 뒤 push합니다.
4. 사용자는 [업데이트](#업데이트) 명령을 실행하고 세션을 다시 시작합니다.

## 10. 변경 내역

버전을 올리는 기준은 [새 버전 배포](#새-버전-배포)를 보세요.

### 0.6.0 (2026-10-29)

**바뀜**

- 사용자가 모델을 지정하지 않으면 서브에이전트를 종류별 기본 모델로 띄웁니다. Explore, claude-code-guide, statusline-setup은 haiku, 기획 세션의 general-purpose는 sonnet, 개발 세션의 general-purpose와 Plan은 세션 모델입니다.
- 안내문을 "서브에이전트의 model은 사용자가 모델을 지정했을 때만 적는다"로 바꿨습니다. 전에는 양이 많고 판단이 적은 일에 메인이 sonnet을 골랐습니다.
- 서브에이전트 opus의 기본 effort를 `max`에서 `high`로 낮췄습니다(`subagentEffort` 기본값 `haiku=low sonnet=high opus=high`).
- 기획 세션이 고치는 일을 직접 하지 못하게 막습니다. 기획 메인은 Bash로 프로젝트 파일이나 git 기록·원격을 바꿀 수 없고, 서브에이전트는 읽기·테스트·임시 폴더 쓰기 외의 Bash와 Edit, Write, NotebookEdit, Monitor를 쓸 수 없습니다.

**수정**

- Claude Code의 작업 목록에서는 사라진 단계가 mod의 목록에만 남아, To-Do 목록이 비워지지 않던 문제를 고쳤습니다. 에이전트가 TaskList를 부르면 그 결과로 목록을 맞추고, `/role`을 다시 입력하면 목록을 새로 시작합니다.

### 0.5.0 (2026-10-29)

**추가**

- `/subagents [n]`: 동시에 일하는 서브에이전트 상한(`maxAgents`)을 보거나 바꿉니다. `0`이면 제한하지 않습니다.
- `/agentEffort [model] [effort]`: 서브에이전트의 모델별 effort(`subagentEffort`)를 보거나 한 모델만 바꿉니다. 레벨은 `l`, `m`, `h`, `xh`, `max`로 줄여 쓸 수 있습니다.
- 두 명령으로 바꾼 값은 `/config`과 같은 플러그인 설정에 저장됩니다. 설정이 변경을 거절하면 이유를 보입니다.

**바뀜**

- 기획 단계가 모두 완료되고 릴레이 행이 모두 통과하면, 그 turn이 끝날 때 To-Do 목록을 비웁니다. 전에는 다음 지시가 올 때까지 남았습니다.

### 0.4.2 (2026-10-28)

**수정**

- `/bin/sh`가 없는 Windows에서도 로그를 씁니다. 로그 파일을 읽고 다시 쓰는 방식입니다.

### 0.4.1 (2026-10-28)

**수정**

- 데스크톱 앱에서 캐릭터를 고정폭 글꼴로 그려 줄을 맞추고, 모델 줄은 작은 글자로 그립니다.
- `/role`이 실패하면 엔진의 `no command.run hook answered it` 문구 대신 `역할 명령 실패 (이유)`를 보입니다.

### 0.4.0 (2026-10-26)

**추가**

- To-Do 목록: 두 세션이 같은 목록을 band에 그립니다. 기획 단계, 릴레이 행, 그 지시의 개발 단계가 함께 보입니다. 에이전트가 TaskCreate·TaskUpdate·TodoWrite로 적은 단계를 모으고, 두 세션은 2초마다 공유 파일로 목록을 주고받습니다.
- 기획 세션이 보고 봉투의 발신자 이름이나 주소로 답장해도 개발 세션에 보내는 지시로 알아봅니다.
- 서브에이전트 정책: 동시 상한 `maxAgents`(기본 3), model 없이 띄운 Explore는 `haiku`, 모델별 effort `subagentEffort`(기본 `haiku=low sonnet=high opus=max`).
- 캐릭터 발 밑에 메인 모델과 effort를 보입니다.

**수정**

- 메인이 띄운 서브에이전트가 일하는 동안은 작업 중으로 봅니다. 개발 보고와 판정 없는 검수 마무리는 서브에이전트가 끝난 뒤로 미룹니다.
- 역할을 다른 세션에 넘긴 세션이 그 세션의 공유 파일을 덮어쓰지 않습니다.
- 긴 To-Do 줄이 있어도 캐릭터와 이름표가 줄어들지 않습니다.
