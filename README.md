# plan-dev-relay

Claude Code 세션 두 개를 **기획 세션**과 **개발 세션**으로 짝지어 주는 mod입니다.

사용자는 기획 세션에만 요청합니다. 기획 세션은 일을 정리해서 개발 세션에 지시하고, 개발 세션은 지시를 받는 즉시 작업합니다. 개발 세션의 작업이 끝나면 결과가 기획 세션에 자동으로 보고됩니다. 기획 세션이 보고를 자동으로 검토하고, 부족하면 다시 지시하게 할 수도 있습니다(`/relay auto`). 오간 지시와 보고, 개발 세션의 작업 내역은 모두 날짜별 로그 파일에 남습니다.

```
            요청                지시 (SendMessage → "dev-session")
  사용자 ─────────▶ 기획 세션 ─────────────────────────────────────▶ 개발 세션
                      ▲                                                 │
                      │          보고 (개발 세션의 작업이 끝나면 자동)    │
                      └─────────────────────────────────────────────────┘

  모든 지시·수신·파일 수정·명령·보고 ──▶ <logRoot>/<repo 이름>/YYYY-MM-DD.md
```

## 1. 역할별로 하는 일

역할은 두 가지 방식으로 동작합니다.

- **안내문**: `/role`을 입력할 때 모델에게 전달되는 규칙입니다. 모델이 이 규칙을 따라 판단합니다. **강제하지는 않습니다.**
- **mod 동작**: mod 코드가 항상 처리하는 일입니다. 모델의 판단과 관계없이 동작합니다.

### 기획 세션 (`/role plan`)

사용자의 요청을 정리하고, 구현·수정·테스트가 필요한 일을 개발 세션에 맡깁니다.

**안내문 (기획 모델이 받는 규칙)**

- 구현, 수정, 테스트 작업은 직접 하지 않고 개발 세션에 지시한다.
- 지시는 SendMessage로 보내고, `to`에는 `"dev-session"`을 쓴다.
- 지시의 첫 줄에는 작업 제목을 쓰고, 이어서 목표, 대상 파일, 완료 조건을 적는다.
- 개발 세션이 등록되지 않았으면 사용자에게 다른 세션에서 `/role dev`를 입력해 달라고 요청한다.
- 개발 세션의 보고는 다음 프롬프트와 함께 오므로, 보고를 기다리며 폴링하지 않는다.

**mod 동작**

- 기획 모델이 `"dev-session"`(또는 개발 세션 id) 앞으로 보낸 메시지를 가로채서, 등록된 개발 세션으로 전달합니다. SendMessage는 세션 id를 주소로 받지 않기 때문에 mod가 대신 보냅니다.
- 개발 세션이 등록되어 있지 않으면 전달을 거절하고, 그 이유를 모델에게 돌려줍니다.
- 보낸 지시를 로그에 `[기획→개발] 지시`로 남깁니다.
- 개발 세션의 보고가 오면 화면에 "개발 보고 도착" 알림을 띄우고 로그에 남깁니다.
- **수동 모드(기본값)**: 보고가 와도 기획 세션은 스스로 작업을 시작하지 않습니다. 보고는 모아 두었다가, 사용자의 다음 프롬프트와 함께 모델에게 전달합니다(사용자 화면에는 보이지 않음).
- **자동 모드(`/relay auto`)**: 보고가 오면 기획 세션이 바로 검토를 시작합니다. 부족하면 다시 지시하고, 충분하면 '검토 완료'라고 답하고 멈춥니다. 자세한 내용은 [보고 검토 방식](#보고-검토-방식-relay)을 보세요.
- 개발 세션이 아닌 다른 수신자에게 보내는 메시지는 표식만 붙여 그대로 보냅니다.

> 안내문은 강제가 아닙니다. 기획 세션에 "직접 고쳐"라고 강하게 요청하면 기획 모델이 직접 파일을 고칠 수도 있습니다. 개발 세션에 맡기려면 "개발 세션에 지시해"라고 요청하세요.

### 개발 세션 (`/role dev`)

기획 세션의 지시를 받아 실제로 코드를 고치고 테스트합니다.

**안내문 (개발 모델이 받는 규칙)**

- 다른 세션이 보낸 메시지는 기획 세션의 작업 지시다.
- 작업 결과는 자동으로 보고되므로, SendMessage로 기획 세션에 따로 답하지 않는다.
- 마지막 답변에는 무엇을 바꿨는지, 테스트 결과, 남은 문제를 적는다.

**mod 동작**

- 짝인 기획 세션의 지시가 오면 그 지시를 "현재 작업"으로 기록합니다. 세션이 쉬고 있으면 바로 작업이 시작됩니다.
- 작업하는 동안 다음을 모읍니다.
  - 수정한 파일: Edit, Write, NotebookEdit 도구로 바꾼 파일
  - 실행한 명령: Bash 명령과 성공/실패
- 작업(turn)이 끝나면 기획 세션에 보고를 보냅니다.
- 보고 형식:

  ```
  [개발 보고] <지시의 첫 줄>

  <개발 모델의 마지막 답변>

  추가로 받은 지시:          ← 작업 중에 지시가 더 왔을 때만
  - <추가 지시의 첫 줄>

  수정 파일 (Edit·Write 도구):
  - src/main/java/.../FooService.java

  명령:
  - 성공: ./gradlew test
  ```

- 마지막 답변이 8,000자를 넘으면 보고에서는 자르고 `전체 내용: <로그 파일 경로>`를 붙입니다. 로그에는 전체가 남습니다.
- 작업이 중단되거나 오류·거절로 끝나면 답변 앞에 `(중단됨)`, `(오류로 종료)`, `(거절로 종료)`를 붙입니다.
- 작업 중에 지시가 또 오면 첫 지시를 유지하고, 새 지시는 보고의 `추가로 받은 지시`에 적습니다.
- 사람이 개발 세션에 직접 입력한 작업은 로그에만 남기고 기획 세션에는 보고하지 않습니다. 직접 입력한 작업을 하는 도중에 지시가 오면 그 지시 작업으로 바뀌고, 그때까지의 기록은 유지됩니다.

### 두 역할 공통

- **상태 줄 캐릭터**: 프롬프트 위에 역할별 Claude 캐릭터를 보여 줍니다. 작업 중에는 움직이고, 쉬는 중에는 흐린 색으로 멈춥니다. 작업 중이면 이름표 옆에 지시 제목이 나옵니다.

  ```
  기획 (파란 이름표)                         개발 (초록 이름표)
              .oO( ? )                        ▄███▄
   ▐▛███▜▌   ┌────────┐                      ▐▛███▜▌   ┌────────┐
  ▝▜█████▛▘──│ ☐ 요구 │   기획 중           ▝▜█████▛▘  │ >_ ▌   │   개발 중
    ▘▘ ▝▝    │ ☐ 설계 │                       ▘▘ ▝▝    └──┬──┬──┘
             └────────┘                                    ═╧══╧═
  ```

- **발신 표식**: 두 세션이 주고받는 메시지 첫 줄에 `[plan-dev-relay role=<역할> session=<세션 id>]` 표식을 붙입니다. 받는 쪽은 이 표식으로 짝의 메시지인지 확인하고, 표식은 지운 뒤 모델에 넘깁니다. 표식이 없거나 짝이 아닌 세션의 메시지는 mod가 건드리지 않습니다. 표식은 구별용이며 보안 장치가 아닙니다.
- **짝 맺기**: repo마다 기획 하나, 개발 하나가 짝이 됩니다. 짝 정보는 `roles.json`에 저장되고, 같은 역할을 다른 세션이 등록하면 그 세션으로 바뀝니다.

## 2. 요구 사항

| 항목 | 내용 |
| --- | --- |
| Claude Code | 2.1.287 이상. mod의 function hooks API는 초기 공개 단계라 버전이 바뀌면 동작이 달라질 수 있습니다. |

## 3. 설치

### 방법 A. 마켓플레이스로 설치 (추천)

이 저장소는 플러그인이면서 마켓플레이스입니다. Claude Code 안에서 두 줄이면 설치됩니다.

```
/plugin marketplace add ssh://git@git.ahha.tf:2222/se1_project/plan-dev-relay.git
/plugin install plan-dev-relay@plan-dev-relay
```

- 위 주소는 사내 GitLab의 SSH 주소입니다. GitLab 계정에 SSH 키가 등록되어 있어야 합니다.
- 이 GitLab에 처음 접속하는 컴퓨터라면 `ssh -p 2222 git@git.ahha.tf`로 한 번 접속해서 호스트 키를 등록하세요.
- 터미널에서 설치할 수도 있습니다.

  ```
  claude plugin marketplace add ssh://git@git.ahha.tf:2222/se1_project/plan-dev-relay.git
  claude plugin install plan-dev-relay@plan-dev-relay
  ```

- 설치한 뒤 **새로 띄운 세션부터** 적용됩니다.
- 설치 확인: 새 세션에서 `/role`을 입력했을 때 `역할 없음. 사용법: /role plan | dev | off`가 나오면 설치된 것입니다.

### 방법 B. 프로젝트에 등록해서 팀원에게 안내하기

팀이 함께 쓰는 프로젝트의 `.claude/settings.json`에 아래 내용을 넣으면, 팀원이 그 프로젝트를 열 때 설치 안내가 나옵니다.

```json
{
  "extraKnownMarketplaces": {
    "plan-dev-relay": {
      "source": { "source": "git", "url": "ssh://git@git.ahha.tf:2222/se1_project/plan-dev-relay.git" }
    }
  },
  "enabledPlugins": { "plan-dev-relay@plan-dev-relay": true }
}
```

직접 고치는 대신 `claude plugin marketplace add <주소> --scope project`를 실행해도 마켓플레이스 등록이 들어갑니다.

### 방법 C. 폴더로 직접 불러오기 (mod를 고치면서 쓸 때)

```
git clone ssh://git@git.ahha.tf:2222/se1_project/plan-dev-relay.git
```

`~/.claude/settings.json`에 clone한 폴더 경로를 넣습니다.

```json
{
  "env": { "CLAUDE_CODE_PLUGIN_DIRS": "/절대/경로/plan-dev-relay" }
}
```

- 한 번만 써 보려면 `claude --plugin-dir /절대/경로/plan-dev-relay`로 실행합니다.
- 실행 중인 세션은 이 폴더를 감시하므로, 파일을 고쳐 저장하면 mod가 다시 불러와집니다.
- **방법 A와 함께 쓰지 마세요.** 같은 mod가 두 번 불려 hook이 두 번 실행됩니다(로그와 보고가 두 번씩 남음).

### 업데이트

```
claude plugin marketplace update plan-dev-relay
claude plugin update plan-dev-relay@plan-dev-relay
```

업데이트는 세션을 다시 시작해야 적용됩니다. 방법 C는 `git pull`만 하면 됩니다.

### 제거

```
claude plugin uninstall plan-dev-relay@plan-dev-relay
claude plugin marketplace remove plan-dev-relay
```

로그 폴더는 지워지지 않습니다. 필요하면 직접 지우세요.

## 4. 설정

| 설정 | 기본값 | 설명 |
| --- | --- | --- |
| `logRoot` (로그 폴더) | `~/Documents/claude/plan-dev-log` | 로그와 `roles.json`을 둘 폴더입니다. repo마다 하위 폴더가 생깁니다. `~`는 홈 폴더로 바뀝니다. |

바꾸는 방법은 셋 중 하나입니다.

- Claude Code의 `/plugin` 메뉴에서 plan-dev-relay를 골라 `로그 폴더`를 바꿉니다.
- 설치할 때 지정합니다.

  ```
  claude plugin install plan-dev-relay@plan-dev-relay --config logRoot=/원하는/경로
  ```

- 설치 뒤 터미널에서 바꿉니다.

  ```
  echo '{"logRoot":"/원하는/경로"}' | claude plugin configure plan-dev-relay@plan-dev-relay --values-stdin
  ```

`claude plugin configure plan-dev-relay@plan-dev-relay`를 옵션 없이 실행하면 현재 설정을 볼 수 있습니다.

## 5. 사용법

### 시작하기

1. 터미널 A에서 repo 폴더로 이동해 `claude`를 실행하고 `/role plan`을 입력합니다.
2. 터미널 B에서 **같은 repo 폴더**로 이동해 `claude`를 실행하고 `/role dev`를 입력합니다.
3. 두 세션의 **권한 모드를 같게** 맞춥니다(예: 둘 다 auto). 다르면 메시지가 승인 대기에 걸릴 수 있습니다([문제 해결](#7-문제-해결) 참고).

### 일 맡기기

1. 기획 세션(A)에 평소처럼 요청합니다.
   - 예: `로그인 API에 입력값 검증을 추가하도록 개발 세션에 지시해`
2. 기획 모델이 지시를 정리해서 개발 세션에 보냅니다.
3. 개발 세션(B)이 지시를 받아 바로 작업합니다. 상태 줄의 개발 캐릭터가 움직입니다.
4. 작업이 끝나면 기획 세션에 "개발 보고 도착" 알림이 뜹니다.
5. 기획 세션에 다음 프롬프트를 보내면 기획 모델이 보고를 읽습니다.
   - 예: `보고 확인해 줘`, `결과 검토해서 다음 작업 정해 줘`

### 보고 검토 방식 (`/relay`)

기획 세션이 개발 보고를 받은 뒤 어떻게 할지 정합니다. 기획 세션에서 입력합니다.

| 모드 | 동작 |
| --- | --- |
| 수동 (기본값, `/relay manual`) | 보고를 모아 두었다가 사용자의 다음 프롬프트와 함께 넘깁니다. 사용자가 "검토하고 부족하면 다시 지시해"라고 하면 기획 모델이 검토합니다. |
| 자동 (`/relay auto`, `/relay auto 5`) | 보고가 오면 기획 세션이 바로 검토합니다. 부족하면 다시 지시하고, 충분하면 '검토 완료'라고 답하고 멈춥니다. 최대 횟수(기본 3회, 1~10)까지 반복합니다. |

자동 모드의 흐름:

```
개발 보고 → 기획 자동 검토 (1/3) → 부족 → 재지시 → 개발 작업 → 보고
          → 기획 자동 검토 (2/3) → 충분 → "검토 완료" (멈춤)
```

자동 검토가 멈추는 경우:

- 기획 모델이 '검토 완료'라고 답하고 더 지시하지 않을 때
- 최대 횟수에 닿았을 때: 그다음 보고는 수동 모드처럼 모아 두고 "자동 검토 N회 도달, 확인이 필요합니다" 알림을 띄웁니다.
- 사용자가 Esc로 작업을 멈추거나 `/relay manual`을 입력할 때

알아 둘 점:

- 사용자가 기획 세션에 직접 프롬프트를 입력하면 자동 검토 횟수가 0으로 돌아갑니다.
- 모드는 세션마다 정해집니다. 세션을 새로 띄우면 수동 모드로 시작합니다.
- 자동 모드는 사람 없이 두 세션이 주고받으므로 토큰을 더 많이 씁니다.

### 명령

| 명령 | 하는 일 |
| --- | --- |
| `/role plan` | 이 세션을 기획 세션으로 등록하고, 기획 안내문을 모델에 전달합니다. |
| `/role dev` | 이 세션을 개발 세션으로 등록하고, 개발 안내문을 모델에 전달합니다. |
| `/role` | 현재 역할과 상대 세션 id를 보여 줍니다. |
| `/role off` | 역할을 지우고 `roles.json`에서 이 세션 항목을 지웁니다. 다른 세션이 같은 역할로 다시 등록했으면 그 항목은 남깁니다. |
| `/relay` | 현재 보고 검토 방식(수동/자동)과 자동 검토 진행 횟수를 보여 줍니다. |
| `/relay manual` | 수동 모드로 바꿉니다(기본값). |
| `/relay auto [N]` | 자동 모드로 바꿉니다. N은 최대 자동 검토 횟수(1~10, 기본 3)입니다. 기획 세션에서만 쓸 수 있습니다. |

### 알아 두면 좋은 점

- 역할은 **세션마다** 정합니다. 세션을 새로 띄우면 `/role`을 다시 입력합니다.
- 개발 세션을 바꾸고 싶으면 새 세션에서 `/role dev`를 입력하면 됩니다. 이전 개발 세션은 짝에서 빠집니다.
- 개발 세션에서도 사람이 직접 작업을 시킬 수 있습니다. 이 작업은 로그에만 남고 기획 세션에는 보고되지 않습니다.

## 6. 로그

| 파일 | 경로 |
| --- | --- |
| 날짜별 로그 | `<logRoot>/<repo 이름>/YYYY-MM-DD.md` |
| 짝 정보 | `<logRoot>/<repo 이름>/roles.json` |

두 세션이 같은 로그 파일에 시간순으로 기록합니다. 기록 예:

```markdown
# control-center plan-dev log 2026-10-14

## 13:49:24 [기획→개발] 지시 (<기획 세션 id> → <개발 세션 id>)
빈 텍스트 파일 생성
목표: 저장소 루트에 빈 텍스트 파일 하나를 만든다.
...

## 13:49:24 [개발] 수신 (<기획 세션 id> → <개발 세션 id>)
...

## 13:50:26 [개발] 명령 성공
`touch empty.txt`

## 13:50:43 [개발→기획] 보고 (<개발 세션 id> → <기획 세션 id>)
[개발 보고] 빈 텍스트 파일 생성
...

## 13:50:43 [기획] 보고 수신 (<개발 세션 id> → <기획 세션 id>)
...
```

| 항목 | 남기는 쪽 | 내용 |
| --- | --- | --- |
| `역할 등록` | 양쪽 | `/role plan`, `/role dev`를 입력한 세션 id |
| `[기획→개발] 지시` | 기획 | 보낸 지시 원문 |
| `[개발] 수신` | 개발 | 받은 지시 원문 |
| `[개발] 파일 수정` | 개발 | Edit·Write 도구로 바꾼 파일 |
| `[개발] 명령 성공/실패` | 개발 | 실행한 Bash 명령 |
| `[개발→기획] 보고` | 개발 | 보낸 보고 (답변 전체) |
| `[기획] 보고 수신` | 기획 | 받은 보고 |
| `[개발] 직접 입력`, `직접 작업 완료` | 개발 | 사람이 직접 입력한 작업과 그 결과 |
| `전달 실패` | 양쪽 | 지시나 보고를 보내지 못한 이유 |
| `[기획] 검토 모드 변경` | 기획 | `/relay`로 바꾼 모드 |
| `[기획] 자동 검토 n/N` | 기획 | 자동 검토를 시작한 회차 |
| `[기획] 자동 검토 한도 도달` | 기획 | 최대 횟수에 닿아 자동 검토를 멈춤 |

## 7. 문제 해결

| 증상 | 원인과 해결 |
| --- | --- |
| 개발 세션이 지시를 받고도 작업을 시작하지 않는다 | 두 세션의 권한 모드 종류가 다르면 Claude Code가 다른 세션의 메시지를 **승인 대기**로 붙잡아 둡니다. 두 세션의 권한 모드를 맞추세요. 항상 받으려면 `~/.claude/settings.json`에 `"crossSessionInbound": "accept"`를 넣을 수 있지만, 내 모든 세션이 서로 작업을 시킬 수 있게 되므로 신중히 쓰세요. |
| 기획 세션에 "개발 세션 전달 실패" 알림이 뜬다 | 개발 세션이 등록되지 않았거나 이미 꺼졌습니다. 개발 세션에서 `/role dev`를 다시 입력하세요. |
| 개발 세션에 "기획 세션 전달 실패" 알림이 뜬다 | 기획 세션이 등록되지 않았거나 꺼졌습니다. 보고 내용은 로그에 남아 있습니다. |
| 기획 모델이 직접 코드를 고친다 | 역할 규칙은 안내문이라 강제되지 않습니다. 요청에 "개발 세션에 지시해"라고 명시하세요. 세션을 새로 띄웠다면 `/role plan`을 다시 입력해 안내문을 전달하세요. |
| 기획 모델이 `dev-session`을 모른다 | 안내문은 `/role`을 입력할 때 전달됩니다. `/role plan`을 다시 입력하세요. |
| 자동 검토가 계속 반복된다 | 기획 모델이 계속 부족하다고 판단하는 경우입니다. 최대 횟수에서 멈추며, Esc를 누르거나 `/relay manual`을 입력하면 바로 멈춥니다. 횟수를 줄이려면 `/relay auto 1`처럼 지정하세요. |
| 자동 모드인데 보고가 와도 검토하지 않는다 | `/relay`로 최대 횟수에 닿았는지 확인하세요. 기획 세션에 프롬프트를 한 번 입력하면 횟수가 초기화됩니다. 두 세션의 권한 모드가 다르면 보고가 승인 대기에 걸릴 수도 있습니다. |
| 로그와 보고가 두 번씩 남는다 | 마켓플레이스 설치(방법 A)와 폴더 불러오기(방법 C)를 함께 쓰고 있습니다. 하나만 쓰세요. |
| 로그 파일이 생기지 않는다 | `logRoot` 경로에 쓰기 권한이 있는지 확인하세요. Windows는 지원하지 않습니다. |
| "roles.json이 깨져서…" 메시지가 보인다 | 짝 정보 파일이 손상되었습니다. 빈 짝 정보로 계속 동작하며, 양쪽에서 `/role`을 다시 입력하면 새로 써집니다. |

## 8. 주의 사항

- **신뢰하는 환경에서만 쓰세요.** 이 mod는 셸 명령(로그 쓰기)을 실행하고, 세션 간 메시지로 다른 세션이 작업을 시작하게 합니다.
- **보고의 "수정 파일"은 Edit·Write·NotebookEdit 도구로 바꾼 파일만 담습니다.** 셸 명령으로 바꾼 파일은 "명령" 목록에서 확인하세요.
- 로그에는 지시와 답변 원문이 그대로 남습니다. 민감한 내용을 다룬다면 로그 폴더 위치와 공유 범위에 주의하세요.

## 9. 개발

### 파일 구조

```
plan-dev-relay/
├── .claude-plugin/
│   ├── plugin.json        # 플러그인 정보, userConfig(logRoot)
│   └── marketplace.json   # 이 저장소를 마켓플레이스로 쓰기 위한 목록 ("./")
├── hooks/
│   ├── hooks.json         # hook 모듈 지정 (register.tsx)
│   ├── register.tsx       # 모든 hook과 $를 쓰는 입출력 함수
│   ├── core.ts            # 순수 함수: 경로, 시각, 표식, 보고, 안내문
│   ├── art.ts             # 순수 함수: 캐릭터 프레임과 이름표 색
│   ├── core.test.ts       # core.ts, art.ts 테스트
│   └── relay.test.ts      # 엔진 수준 시나리오 테스트
└── types/index.d.ts       # $.state 값의 타입 계약
```

### 검증

```
claude plugin test .
claude plugin validate --strict .
claude plugin validate --strict .claude-plugin/plugin.json
```

### 엔진 규칙 (고칠 때 주의)

엔진은 hook 모듈을 불러오기 전에 소스를 검사합니다. 아래 규칙을 어기면 mod가 불려지지 않습니다.

- `$`를 받는 함수는 `register.tsx` 안에 선언해야 합니다. 다른 파일에서 가져온 함수에 `$`를 넘길 수 없습니다.
- `atom({ plugin, key })`의 `plugin`과 `key`는 문자열 리터럴이어야 합니다.
- `$.env.get`의 변수 이름은 문자열 리터럴이어야 합니다.
- 테스트에서 `$` 호출(`session.id`, `fs.*`, `process.run` 등)에 답하는 stub은 `{ value }`로 감싸서 돌려줘야 합니다.

### 새 버전 배포

1. `.claude-plugin/plugin.json`과 `.claude-plugin/marketplace.json`의 `version`을 함께 올립니다.
2. 테스트와 검증을 통과시킨 뒤 push합니다.
3. 사용자는 [업데이트](#업데이트) 명령을 실행하고 세션을 다시 시작합니다.
